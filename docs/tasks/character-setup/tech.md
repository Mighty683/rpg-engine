# Character setup — technical design

**Created:** 2026-11-05
**Related:** [Story](story.md) · [UX journey](ux.md) · [Fabula Ultima specification](fabula-ultima-character-spec.md)

## Current situation

The application creates and lists persisted games. [Games](../../../packages/backend/src/modules/games) validates a fixed system ID and stores it in PostgreSQL; the [system catalog](../../../packages/backend/src/modules/rpg-systems/catalog.ts) contains only `dnd-5e`. The frontend has one route and no game detail, player, or character workflow. The [migration runner](../../../packages/backend/src/migrate.ts) executes only `001_games.sql`; adding a migration file alone will not run it. Existing API tests use a mocked pool, while frontend browser tests mock responses; full-stack scenarios live in `packages/tests`.

The story and UX are proposals, not validated product behavior. The supplied rules describe creation and class benefits, but the referenced 75-skill index is absent from this repository and individual skill effects, choices, spells and the full item catalog are not supplied. The three example items are test fixtures, not a complete catalog. Starting cash is explicitly deferred by the UX. Full mechanical completion cannot be honestly implemented or validated until the required rule data is supplied.

## Decision record

- **System boundary:** add a stable Fabula Ultima system ID to the existing catalog without changing `dnd-5e` or existing game records. Gate Fabula setup on the persisted game's system on the server as well as in the UI. System identity and a versioned rules catalog are different concepts; save the catalog version used by each character and retain it for existing characters.
- **Ownership:** a player belongs to one game; a character belongs to one player. Multiple characters may exist per player, at most one active. Incomplete/complete and active/inactive are separate states; activation must not be implied by completion. Enforce ownership and the active-character invariant in PostgreSQL, including concurrent updates.
- **Characters are durable source data:** persist incomplete and temporarily inconsistent selections, with structured issues returned for display. There is no separate draft or save action; edits appear optimistically and are persisted asynchronously. Validate request shape and ownership on every update; enforce creation rules on completion. Do not delete dependent selections when a choice changes. A completed character remains editable, but an edit that would invalidate completion must be resolved before it is committed as completed; preserve the unsaved input and explain the issues.
- **Rules remain system-specific:** keep generic game/player/character identity and persistence separate from a Fabula rules module. Store selections and mutable resources as authoritative data; calculate derived values deterministically from those selections and the pinned catalog. Do not store a derived sheet as the only source of truth or invent missing effects. Report unavailable calculations and validation as incomplete, never as zero or valid.
- **Completion is gated by evidence:** missing catalogs or unsupported required effects block a claim of a rules-complete character. Incomplete character updates and partial calculations may still work, clearly marked. Cash calculation and starting cash rolls are excluded from this task under the UX decision; they must not silently block completion of the agreed reduced scope. Record this deviation from the rules specification visibly in the product and in any later cash design.
- **Single GM is not authentication:** the existing trusted-environment assumption remains; this design does not add user accounts or access control.

## Implementation spec

### Persistence and lifecycle

Add forward-only, repeatable migrations for players and characters, and update the migration runner to apply them to both new and existing databases without modifying or dropping saved games. Players have stable UUIDs, game foreign keys and required trimmed names; duplicate names do not identify records. Characters have stable UUIDs, player foreign keys, an incomplete/complete state, independent active flag, ruleset/version, versioned structured selections, revision, and timestamps. Use a partial unique index on player ID for active characters; activation/deactivation must be atomic. Check that the game, player and character path agree on every operation. Define a schema-version migration strategy before changing the stored selection shape or removing catalog versions.

Incomplete characters may omit mandatory fields and contain mechanically invalid combinations, but must have a bounded, structurally valid payload and known schema version. Use stable IDs for classes, skills and equipment, preserving unresolved selections when rules or dependencies change. Keep character names within the selections so an unnamed character can exist. On first successful completion initialize current HP, MP and IP from available maxima and Fabula points to 3 once, in the same transaction as the state transition. Later edits and retries must not refill resources. Do not implement advancement, bonds, statuses, world/party management or full combat as part of this setup; leave room for them without claiming support.

### Rules and calculations

The Fabula module owns catalog lookup, issue reporting, completion validation and pure calculation. At creation validate required identity, theme, origin and presentation; 2–3 distinct classes totaling five levels; five skill ranks allocated within their own classes and catalog caps and required choices; one permitted starting dice multiset; and supported starting equipment, slots, hand use and martial entitlements. Use the supplied specification for the exact requirements and distinguish data-unavailable issues from invalid choices. Class benefits apply once per distinct class and stack across classes. HP and MP use base MIG/WLP; defense uses current dice with the applicable armor replacement/offset and shield rules. Apply skill and equipment effects only where sourced and implemented; expose partial results as such. Do not infer missing effects or claim the three sample items represent all legal purchases.

Persist catalog identifiers and structured skill choices, equipment instances and slot assignments. Calculate from the persisted source and pinned catalog on load and after edits; do not reroll or fabricate missing data. Catalog version changes require an explicit compatibility or migration decision, not reinterpretation against the latest catalog. The supplied Camilla example is useful for regression only where its underlying effects are actually supplied.

### Application and HTTP boundary

Extend the existing controllers/services and error envelope. Provide game detail, player list/create, character list/create/read/save, completion and activation operations scoped to the parent game/player. IDs in requests are checked against their parents; unknown or mismatched resources return a consistent not-found response. Return field/step-addressable issues and distinguish malformed payloads (400), invalid commands (422), missing resources (404), and stale revisions (409). Server validation remains authoritative. Non-Fabula games cannot create or mutate Fabula profiles.

Use a client-generated character UUID for character creation and a conditional revision for updates and completion. Persist each mutation and its revision atomically; reject stale writes rather than overwriting another view. After an uncertain response, read the known ID and revision before retrying; retain local input and reconcile if the saved version differs. Creation retries for the same ID must not create duplicates or silently replace a different payload. Player creation also needs a stable request identity or an explicit check-before-retry flow because duplicate names are allowed. Existing game-creation behavior and API contracts remain compatible.

### Frontend and verification

Add routes for opening a game, managing its players and selecting or creating their characters. The shared character card supports viewing and in-place editing on the same screen for players and the GM. Access and permissions require a separate design. The card owns an optimistic local copy and saved revision, pending/failed/unknown update states and review issues. Queue or reconcile overlapping updates so stale responses cannot overwrite newer edits; retain failed changes and offer recovery. Map server issues to steps, preserve input on errors and dependency changes, and re-read saved state after an uncertain outcome. Reuse existing Vue, i18n and `data-testid` conventions; do not imply unavailable calculations are complete.

Follow [testing conventions](../../spec/testing.md). Cover rule branches with pure unit tests, including class bonus stacking, attribute permutations, skill allocation and equipment constraints where catalog data exists. Exercise incomplete versus complete characters, parent/system checks, stale revisions, idempotent retry, one-active-character concurrency and one-time resource initialization through API and real PostgreSQL integration tests. Verify migration from an existing games database and persistence after restart. Browser component tests cover navigation, incomplete characters, invalidated choices, update failures and unknown outcomes; full-stack tests cover a supported creation/resume journey. Mark catalog-dependent tests blocked until sourced data and effects are available; do not replace them with invented fixtures.
